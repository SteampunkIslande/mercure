# Exemple d'un cycle de vie d'un formulaire

Ci-dessous, un exemple de timeline pour comprendre les différentes étapes dans le développement, le déploiement et l'exécution d'un pipeline avec Mercure.

- Etape 1: un bioinformaticien a développé une version de launcher qui lui convient dans `/OPT/pipelines-dev`. Il ajoute ses modifications à la validation (`git add`), les valide (`git commit -m '...'`) et les pousse (`git push`). A ce moment, aucun formulaire n'est encore associé à ce launcher qu'il vient de développer. Le commit auquel appartient ce nouveau launcher est `420ab`.
- Etape 2: le même bioinformaticien crée un formulaire dans Mercure. Dans la page de définition du formulaire, il indique le launcher qu'il vient de créer, et définit les types des variables requises par le launcher ainsi que les valeurs par défaut associées le cas échéant. Mercure enregistre dans sa base de données un nouveau formulaire, avec l'id `1`, et la dernière révision du launcher définie à `420ab`.
- Etape 3: un utilisateur déclare un run avec le formulaire `1`. Cela crée alors un Run avec l'id `1`, qui enregistre que le formulaire utilisé est le formulaire `1`. Le run `1` est `Idle`.
- Etape 4: l'utilisateur qui a déclaré le Run 1 pour le formulaire 1 le valide. Le Run 1, pour le formulaire 1, est maintenant au statut `Pending`. Ce qui a créé la tentative 1 du run 1.
- Etape 5: un bioinformaticien vient de modifier le pipeline utilisé par le formulaire `1` du run `1`, il a `git addd`, `git commit` et `git push`. A présent, la dernière révision du launcher n'est plus `420ab` mais `421cd`. Seulement, la routine sait qu'il y a au moins un run au statut `Pending`. Et le run n'est pas terminé sur le séquenceur, donc la routine ne met pas encore à jour le dossier pipelines.
- Etape 6: Le run 1 vient de se terminer sur le séquenceur, le script exécuté par la routine l'a détecté, ce qui déclenche la création par la routine d'un script dans `/OPT/JOBS/TODO/job-0000000001-0000000001.sh`. A ce moment-là, il se passe deux choses. D'abord, la routine a écrit, dans ce script `job-0000000001-0000000001.sh`, tout le contenu du launcher à la révision `420ab`. La routine passe alors le run 1 et la tentative 1 associée à l'état `Running`. Ensuite, dans un deuxième temps, la routine exécute `git pull` (en supposant que dans ce cas simple, il n'y a pas d'autre run en mode `Pending`). Le dossier /OPT/pipelines est alors à jour avec /OPT/pipelines-dev, ce qui rend obsolète tous les formulaires dont le launcher a été modifié entre temps. Ce qui est le cas du formulaire 1.
- Etape 7: Le formulaire 1 est maintenant automatiquement marqué comme archivé: s'il y avait des runs à l'état Idle utilisant ce formulaire, en raison de la discordance entre la dernière révision constatée du launcher et celle qui était enregistrée dans la base, ceux-ci ne seront plus consultables tant qu'un adminsitrateur n'aura pas demandé la mise à jour du formulaire (via une page dédiée). Les runs en cours d'exécution ne sont pas affectés, simplement l'utilisateur est certain que le code du launcher qui est en train de s'exécuter correspond à ce qu'il était au moment où le run a été validé. Quant aux runs terminés (avec succès ou avec une erreur), il ne sera pas possible de les relancer tels quels, mais ils seront visibles. Enfin, si un run avait été relancé ou déclaré avant la mise à jour du launcher, ce dernier ne sera plus accessible (même en lecture), et un message avertira l'utilisateur que le pipeline a été archivé.
- Etape 8: Supposons que les changements appliqués au launcher n'en modifient pas la fonctionnalité et que les résultats sont identiques. Il s'agit d'ajustements à la marge, comme par exemple un changement d'adresse d'un dépôt, l'ajout d'une adresse mail de contact, etc. Dans ce cas, on ne peut pas vraiment dire que les formulaires associés soient obsolètes. Il est donc possible, pour un administrateur, de prendre la responsabilité de "mettre à jour" un pipeline marqué comme archivé, ce qui consiste à simplement ré-enregistrer dans la base le numéro de la dernière révision constatée du launcher. Cette opération n'est possible que si les UDV (variables définies par l'utilisateur) sont rigoureusement identiques d'un launcher à l'autre.
